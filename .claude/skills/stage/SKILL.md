# stage

인자: `$ARGUMENTS`

- 첫 값은 두 자리 단계 번호(NN)다. 예: `02`
- 두 번째 값은 모드(`plan`, `run`, `doc`, `retro`)다. 없으면 "상태 판정"으로 다음 모드를 정해 사용자에게 제안하고 멈춘다.

## 공통 규칙

- 도구 추천과 단계 디렉토리 매핑은 `docs/dev-process/skillset-by-lifecycle.md`만 따른다. 이 스킬에는 도구 이름을 적지 않는다.
- `CLAUDE.md`의 고정 결정을 따른다.
- 경로(`<DIR>`는 lifecycle 문서 `디렉토리` 열의 값):
  - 계획: `docs/dev-process/<DIR>-plan.md`
  - 기록: `docs/dev-process/<DIR>/`
  - 입력: `docs/<DIR>/input/`. 앞 단계 output은 복사하지 않고 링크한다.
  - 산출물: `docs/<DIR>/output/`
  - 최종 문서: `docs/<DIR>/output/<파일>`. 파일 이름은 `templates/output-types.md`의 NN 행을 따른다.
- 도구 동작, 설치 상태, 한도 같은 사실은 확인한 것만 쓴다. 확인한 날짜와 출처를 남긴다. 확인하지 못한 것은 "미확인"으로 적는다.
- 날짜는 절대 날짜(YYYY-MM-DD)로 쓴다.

## 단계 결정

1. lifecycle 문서의 "단계별 추천" 표에서 `디렉토리` 값이 `NN-`로 시작하는 행을 찾는다. 없으면 멈추고 알린다.
2. 그 행의 1순위, 보조, 이유 열을 읽는다.
3. "이 프로젝트의 선택" 절을 읽는다. 여기의 제외 규칙과 겹침 규칙이 행보다 우선한다.

## 상태 판정

| 상태 | 다음 모드 |
| --- | --- |
| 계획 파일 없음 | `plan` |
| 계획 파일에 상태 줄이 없음 | 이 스킬을 쓰기 전에 만든 계획이다. 파일을 고치지 않고 그렇다고 알린 뒤 멈춘다 |
| 계획 파일의 상태 줄이 "초안" | 사용자 검토 대기. 승인을 묻는다 |
| 상태가 "승인"이고 "완료"가 아닌 기록 파일이 있거나 남은 단계가 있음 | `run` |
| 모든 단계 기록이 "완료"이고 최종 문서가 없거나 문서 상태가 "확정"이 아님 | `doc` |
| 최종 문서가 "확정"이고 회고 파일 없음 | `retro` |
| 회고 파일 있음 | 이 단계는 끝났다고 알린다 |

## plan

1. "단계 결정"을 수행한다.
2. 입력을 정리한다. `docs/<DIR>/input/`의 파일과 직전 단계의 `output/`을 확인한다. 직전 단계 output이 비어 있으면 알리고, 계속할지 묻는다.
3. 쓸 도구를 고른다. 행의 1순위와 보조를 "이 프로젝트의 선택" 절로 거른다. 고른 이유와 뺀 이유를 모두 계획에 남긴다.
4. 고른 도구마다 이 환경의 상태를 확인한다.
   - 스킬: 이 세션의 사용 가능한 스킬 목록에 있는지 본다.
   - MCP: 도구를 로드하고, 상태를 바꾸지 않는 호출로 연결을 확인한다.
   - 미설치: 설치하지 않는다. README에서 설치 영향(전역 등록, 훅, `CLAUDE.md` 수정, 빌드)을 확인해 위험 표에 적고 결정은 사용자에게 맡긴다.
5. 도구별 저장소 README를 다시 읽는다. 링크는 lifecycle 문서의 "참고 링크"에 있다. 계획에 쓸 동작만 요약하고, 확인 날짜를 계획의 "근거" 줄에 적는다.
6. `templates/plan.md`를 채워 계획 파일을 쓴다.
   - 계획 파일이 이미 있으면 새로 쓰지 않는다. 고치고, 상단에 "수정:" 줄을 추가한다.
   - 작성 예시는 `docs/dev-process/01-requirements-plan.md`다. 구성만 참고하고, 그 단계에만 해당하는 내용은 옮기지 않는다.
7. 멈춘다. 계획 파일 경로, 닫아야 할 결정, 사전 조건만 보고하고 승인을 기다린다. 사용자가 승인하면 상태 줄을 "승인 (YYYY-MM-DD)"로 바꾼다.

## run

1. 계획의 상태가 "승인"이 아니면 멈추고 알린다.
2. 계획의 "진행 순서"를 위에서부터 수행한다. 기록 파일이 "완료"인 단계는 건너뛴다. 세션이 끊겨도 이 방식으로 이어서 한다.
3. 각 단계에서 다음을 한다.
   1. 시작할 때 `templates/record.md`로 기록 파일 `docs/dev-process/<DIR>/0K-<도구>.md`를 만든다. 상태는 "진행 중", 시작 시각을 적는다.
   2. 계획에 적힌 도구를 쓴다. 스킬은 Skill 도구로, MCP는 해당 도구로 부른다. 계획에 없는 도구로 바꾸지 않는다.
   3. 질문과 답, 결정, 계획과 다른 점을 그때그때 기록 파일에 적는다.
   4. 계획의 "끝나는 조건"을 확인한다. 충족하면 요약을 사용자에게 보이고 확인받는다. 확인받으면 상태를 "완료"로 바꾸고 완료 시각을 적는다.
4. 도구가 실패하면 계획의 위험 표에 적힌 대응을 따른다. 대응이 없거나 대응도 실패하면 멈추고 묻는다. 다른 도구나 방법으로 바꾸면 계획 상단에 "수정:" 줄을 남긴다.
5. 산출물은 계획에 적힌 `output/` 경로에 쓴다. 처음에는 초안으로 표시하고, 사용자가 검토한 뒤 확정한다.
   - 코드를 다루는 단계는 코드를 `docs/` 밖에 둔다. `output/`에는 코드 경로와 검증 결과를 적은 요약 문서만 둔다.
   - 최종 문서 초안을 이 모드에서 써도 된다. 형식은 `doc` 모드가 맞춘다.
6. 모든 단계가 끝나면 `doc`를 제안한다.

## doc

이 단계의 결과를 소프트웨어 아키텍처 관점의 정형 문서 하나로 정리한다. 문서는 제품에 대한 최종 내용만 담는다. 결정에 이른 과정은 기록 파일에 둔다.

1. 계획의 모든 단계 기록이 "완료"가 아니면 멈추고 알린다.
2. `templates/output-types.md`에서 NN 행을 찾아 문서 유형, 파일 이름, 장 구성을 정한다. 행이 없으면 멈추고 알린다.
3. 기록 파일 `docs/dev-process/<DIR>/0K-output.md`를 `templates/record.md`로 만든다. K는 마지막 기록 파일 번호의 다음 번호다.
4. 재료를 모은다.
   - 이 단계 `output/`의 작업 산출물
   - 기록 파일들의 "결정" 표
   - 이전 단계 최종 문서. 그 문서의 ID 목록을 추적 대상으로 삼는다.
5. 재료를 둘로 나눈다.
   - 최종 내용: 결정의 결과, 결정 이유, 검토한 대안, 규칙, 구조, 값, 완료 조건
   - 과정 기록: 질문과 답, 작성 경위(어느 계획 단계에서 썼는지, 누구의 지적으로 더했는지), 결정 출처, 일정과 축소 판단, 다음 단계 작업 분해, 개발 도구·모델 권고, 도구 이름과 사용 이력
   - 과정 기록은 문서에 넣지 않는다. 기록 파일의 "옮긴 과정 기록" 절에 원래 위치와 함께 옮기고, 문서에서 그 파일을 링크한다.
   - 결정 시점(이 단계에서 닫음, 다음 단계로 넘김)으로 나뉜 내용은 주제별 절로 다시 모은다. 같은 주제가 여러 절에 흩어지지 않게 한다.
6. `templates/output.md` 골격에 유형별 장을 채워 최종 문서를 쓴다. 규칙:
   - 이전 단계 ID는 그대로 쓴다. 다른 문서(Seed 등)가 참조하는 ID와 절 번호가 바뀌면 그 문서의 참조도 고친다.
   - 새 요소는 `output-types.md`의 공통 ID 접두어로 매긴다.
   - 01 단계는 요구사항 하나마다 개별 ID, 우선순위, 검증 방법을 붙인다.
   - 02 이후는 요구사항 추적표에 상위 ID를 모두 적는다. 대응하는 절이 없는 ID는 "별도 절 없음"으로 남긴다. 지어서 채우지 않는다.
   - 기록에 없는 이유나 대안은 "-"로 둔다. 새로 쓴 내용(용어 정의, 목표 표, 도식, 추적표)은 기존 문장에서 끌어낸다.
   - 표를 기본으로 쓴다. 한 칸에 한 사실만 쓴다.
   - 구조, 상태, 흐름은 mermaid로 그린다.
   - 확인하지 못한 값은 "미확인"으로 쓰고 1장 "다음 단계에서 확인할 항목"에 모은다.
   - 개발 도구(스킬, 플러그인, 에이전트) 이름은 쓰지 않는다. 제품이 쓰는 기술 스택과 요구사항이 정한 외부 시스템은 쓴다.
   - 문체는 짧은 평서문("~다")이다. 한 문장에 한 사실만 쓴다.
   - 이전 단계 문서와 다른 내용은 쓰지 않는다. 이전 단계 문서를 바꿔야 하면 멈추고 사용자에게 차이를 보인다. 승인되면 그 문서를 고치고 개정 이력에 남긴다.
7. 최종 문서가 이미 있으면 새로 쓰지 않고 고친다.
   - 버전을 올린다. 형식만 바꾸면 소수 자리를, 내용을 바꾸면 정수 자리를 올린다.
   - 개정 이력에 바꾼 내용과 옮긴 곳을 적는다. 형식만 바꿨으면 "<요구사항|설계> 내용은 바꾸지 않았다"고 적는다.
8. 사용자에게 보이기 전에 점검한다. 결과는 기록 파일 "끝나는 조건 확인"에 적는다.
   - 유형별 장이 모두 있다. 해당 없는 장은 이유가 있다.
   - 02 이후: 상위 문서 ID가 모두 요구사항 추적표에 있다.
   - 문서 안 링크와 절 번호 참조가 실제 대상을 가리킨다.
   - 과정 기록이 문서에 남아 있지 않다.
   - 본문의 "미확인"이 모두 1장 확인 항목 표에 있다.
9. 초안을 보이고 멈춘다. 사용자가 검토하고 승인하면 문서 상태를 "확정", 버전을 1.0(이미 확정본이 있었으면 7번 규칙의 버전)으로 바꾸고 기록 파일을 "완료"로 바꾼다.
10. `retro`를 제안한다.

## retro

1. 계획 파일과 기록 파일을 모두 읽는다.
2. `templates/retro.md`로 기록 디렉토리에 회고 파일을 쓴다. 파일 번호는 마지막 기록 파일 번호의 다음 번호다. 예: `04-retro.md`
3. 수치는 기록 파일에서 센다. 걸린 시간은 기록 파일의 시작과 완료 시각으로 계산한다. 셀 수 없는 항목은 "미확인"으로 적는다.
4. 결론이 lifecycle 문서와 다르면 수정안을 회고 파일에 적고 사용자에게 보인다. lifecycle 문서는 직접 고치지 않는다.
