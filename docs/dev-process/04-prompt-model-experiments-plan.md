## 쉬운 설명

이 절은 계획 전체를 쉬운 말로 줄인 것이다. 자세한 값은 1장부터 있다.

### 지금 앱 상황

이 앱에서는 AI 두 개가 일한다.

- 만드는 AI: 공식 문서를 읽고 문제와 해설을 쓴다.
- 검사하는 AI(Judge): 만든 문제가 괜찮은지 보고 통과시키거나 버린다.

03 단계에서 이렇게 문제 60개를 만들었다. 그 과정에서 문제점 두 개가 드러났다.

1. 검사 AI가 너무 너그럽다. 209번 검사해서 204번을 통과시켰다. 그런데 사람이 직접 감사했을 때 해설이 틀린 문제, 지문이 정답을 알려 주는 문제가 여러 개 나왔다. 검사 AI는 이것을 못 잡았다.
2. 만드는 AI가 문서를 그대로 베끼지 못한다. 근거로 든 인용이 원문과 달라서 다시 만든 경우가 많았다. 첫 시도 209번 중 116번이 그랬다. 그만큼 시간과 돈이 더 들었다.

### 이 단계에서 하는 일

AI에게 주는 지시문(프롬프트)을 고친 새 버전을 만든다. 원래 버전과 나란히 돌려 정말 나아지는지 숫자로 비교한다. 나아지면 새 버전으로 바꾼다.

- 실험 1(검사 AI): 문제 있는 문항과 멀쩡한 문항을 섞어 검사 AI에게 준다. 문제 있는 문항은 감사에서 찾은 것과 일부러 망가뜨린 것이다. 원래 지시문과 새 지시문 중 어느 쪽이 나쁜 문제를 더 잘 걸러내는지 센다. 더 싼 예비 모델로도 같이 해 본다.
- 실험 2(만드는 AI): 같은 12문제를 원래 지시문과 새 지시문으로 각각 만든다. 인용 실패가 줄었는지, 비용은 어떤지 비교한다.

기존 문제 60개와 운영 DB(`data/quiz.db`)는 건드리지 않는다. 실험은 따로 만든 실험용 DB에서만 한다.

제품이 쓰는 기술(도구 선택 대상 아님):

- Bedrock(NFR-2, NFR-4): 실험 호출. 단가는 `data/pricing/bedrock.yaml`을 쓴다. 리전 전환은 `llm.failover_chain`을 그대로 쓴다.
- Langfuse(NFR-5): 실험 배치도 `batch_id` 태그로 trace가 남는다. 꺼도 돈다(NFR-5.4).

고르지 않은 도구:

- ouroboros `evolve`: README는 세대마다 Seed 온톨로지가 바뀌고 유사도 0.95에서 수렴한다고 설명한다. 프롬프트를 바꾼다거나 A/B를 한다는 설명은 없다. 이 앱의 생성·Judge 파이프라인을 측정하지 않는다. "이 프로젝트의 선택" 절의 계획 도구 하나 규칙에도 걸린다.
- paperthin `readchk`: "이 프로젝트의 선택" 절이 요구사항 단계에만 두었다.
- paperthin `re0-plan`, `re0-loop`: "이 프로젝트의 선택" 절이 계획 도구와 겹친다고 제외했다.
- gstack, gajae-code: "이 프로젝트의 선택" 절이 제외했다.

`mandela`는 lifecycle 4행이 아니라 5행의 보조다. "이 프로젝트의 선택" 절은 paperthin을 필요한 것만 얹게 한다. 이 단계의 결론은 측정 결과라서 평가 누수 점검이 필요하다. 그래서 넣는다. 호출할 때마다 기록 파일에 호출 줄을 남긴다.

도구 설명 요약:

- pstack `/arena`(`skills/arena/SKILL.md`, 2026-11-05):
  - 6단계다. A 과제 정의와 채점 기준 3~6개, B 후보 N개를 백그라운드로 한 메시지에서 띄움, C 읽기 전용 교차 Judge, D 기반 고르기, E 손으로 옮기기, F 검증.
  - 후보는 모두 같은 과제 프롬프트를 받는다. 채점 기준은 후보에게 주지 않는다. 교차 Judge만 채점 기준을 본다.
  - 교차 Judge는 부모와 다른 모델 계열이어야 한다. 다른 계열을 못 쓰면 Judge를 건너뛰고 그렇다고 적는다.
  - 후보가 크게 갈리면 과제 정의를 고쳐 다시 돌린다. 모이면 합의된 모양을 쓴다.
  - 결과는 합성 산출물 하나와 합성 노트(기반과 이유, Judge 판정 또는 생략, 옮긴 것과 출처, 버린 것과 이유, 검증 결과)다.
  - 모델 설정(`~/.cursor/rules/pstack-models.mdc`)과 모델 이름(`grok-*`)은 Cursor 기준이다.
- ouroboros `evolve`(README, 2026-11-05): 온톨로지 유사도 0.95 이상에서 수렴, 최대 30세대다.
- `mandela`(SKILL.md, 2026-11-05): 외부 정답이 독립적으로 들어오는지 본다. 누수 유형 8개 중 해당하는 것만 내고 보완안을 준다. 읽기 전용이다.

## 3. 진행 순서

단계 사이의 선후 관계:

```
0 → 1-가(W1, 코드) ─────────────┐
  → 1-나(데이터셋) → [라벨 확인] ─┼→ 3(EXP-1) → 4(EXP-2) → 5(점검, [채택 승인]) → doc → retro
  → 2 A~E(변형 작성) ──→ 2 F ────┘
                       ↑ 1-가 병합 뒤
```

- 1-가, 1-나, 2단계 A~E는 0단계 뒤 동시에 시작한다.
- 2단계 F(변형 검증)는 1-가 코드가 병합된 뒤에 한다.
- 3단계는 셋이 모두 끝나고, 사용자가 EXP-1 라벨 목록을 확인한 뒤에 시작한다.
- 3, 4단계는 일일 토큰 한도 때문에 차례로 한다.

### 0단계: 사전 준비

1. 1장 결정 1~8을 닫는다. (2026-11-05 완료)
2. `cd app && uv run pytest`가 통과하는지 본다.
3. `data/quiz.db`의 테이블별 행 수를 기록한다. 5단계 끝에 다시 세어 같은지 본다.
4. 커밋되지 않은 변경을 커밋한다. 워커가 이 커밋에서 갈라진다(stage 스킬 run 3번).
5. 기록 파일마다 시작·완료 시각과 세션 모델·추론 강도를 남긴다(03 회고 lifecycle 밖 수정안). 이 규칙은 모든 단계에 적용한다.

### 1단계: 실험 하네스와 데이터셋

- 하는 일: 1-가는 워커 W1이, 1-나는 코디네이터가 동시에 한다.
- 1-가. 하네스 코드(W1, 격리 worktree). 테스트를 먼저 쓴다.

  3. 결정 6: `JUDGE_ITEMS`를 프롬프트 디렉토리 설정으로 늘릴 수 있게 한다. 기본값은 지금 4+2개다.

  8. 커밋하고 브랜치와 커밋 해시를 보고한다. 코디네이터가 병합하고 전체 테스트를 다시 돌린다.

  4. 정상 문항을 고른다. 감사에서 내용 지적이 없는 문항(수는 미확인)과, 교차 풀이 두 모델이 정답 키와 일치한 풀 문항을 더한다. 둘은 따로 집계한다.

  7. EXP-2 슬롯 목록 `data/experiments/EXP-2/slots.json`을 만든다. 12슬롯(버킷당 2, 형식 4종이 3개씩)이다. 실패 사례가 있던 주제와 겹치지 않게 뽑는다. 시드를 기록한다.

### 2단계: arena 방법으로 변형 만들기
