## 제안된 의도

> CCA-F, LangChain 후보 중 하나를 고르고 근거 방식은 설계안 A(docs MCP 직접)로 두어, 두 문서에 흩어진 결정과 열린 질문을 `requirements.md` 하나로 묶는다.

근거로 든 것:

- 두 후보 문서가 모두 "다른 버전과 비교해 최종 선택"으로 끝나고, 앱 구조·MVP·형식·평가가 거의 같다.
- 설계안 B는 A의 확장이고 "L2 오류율이 높으면 A안으로 복귀"라고 스스로 적는다.
- 공통 스택은 후보와 무관하고, 미확인 사항(Bedrock 모델 ID·리전, Langfuse 호스팅)이 남아 있다.

대안 해석으로 "후보 선택보다 근거 방식(A/B) 결정이 먼저"를 함께 제시했다.

## 사용자 수정

| 순서 | 수정 내용 | 반영 방향 |
| --- | --- | --- |
| 1 | "하루 10문제" 단위가 어색하다. 하루 중 언제든 사이클을 수행할 수 있어야 한다 | "세트(10문제) 단위, 횟수 제한 없음". "다음 날 출제에 반영"은 "다음 세트 생성에 반영"으로 바꾼다. CCA-F의 "남은 일수 × 10문제" 공식은 없앤다 |
| 2 | LangChain 후보의 코드형 문제 재료는 공식 문서 예시 코드를 우선한다 | 1순위 공식 문서 예시 코드, 2순위 실습 `.py`. 실습 코드는 문서 예시가 없는 주제와 "자주 하는 실수" 기반 에러 원인 문제에 쓴다. 출제 범위(노트에 있는 주제만)는 유지한다. "코드 보기"는 공식 문서 페이지로 연결한다 |
| 3 | 후보 선택보다 근거 방식(A/B)을 먼저 깊이 검토하고 싶다 | 구현 난이도, 추가 스펙, 레이턴시로 비교한 뒤 **A안으로 확정**. B안은 MVP 이후 실험으로 남긴다 |

### A안 확정 근거 요약

- B안은 A안의 상위집합이라 구현이 줄지 않는다. 공식 OpenWiki personal mode 페이지에서 Bedrock 설정, `custom-mcp` 설정 형식, Windows 지원, 외부 조회 방법을 확인하지 못했다(2026-11-04).
- B안은 ingest 주기, L2 변경 시 재검증, L2 오류율과 중단 기준, OpenWiki 버전 고정(0.3.3 이상), ingest 비용 측정(Langfuse 미연동), 저장소 밖 데이터 위치를 추가로 정해야 한다.
- 레이턴시: 정답 근거는 항상 L1 원문과 대조하므로 B안도 L1 조회를 없애지 못한다. 풀이 경로(사전 생성 풀 사용 시)는 차이가 없고, 생성 경로는 B안이 L2 읽기만큼 길다. B안만 오프라인 ingest 시간과 토큰 비용이 생긴다. 수치는 측정 전이다.
- B안 재검토 조건: A안 파일럿에서 통합형 문제 품질 부족이 확인되고, Windows에서 `custom-mcp` 연결이 확인될 때.
