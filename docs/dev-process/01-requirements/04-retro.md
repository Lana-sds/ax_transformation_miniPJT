- 맥락으로 풀린 것(질문 없이 진행):

- 질문으로 올린 갈림길: "기존 문서"를 어디까지 고칠지. 입력 문서 본문을 고치면 기록이 바뀌고 내용이 두 곳에 생긴다. 고치지 않으면 낡은 표현이 남는다.
  - 답: 안내만 추가한다. `requirements.md`를 단일 기준으로 둔다.

### 초안 검토에서 닫은 결정

초안을 쓰면서 앞 기록에 명시되지 않은 항목 5개가 드러났다. 사용자가 검토 중에 모두 닫았다.

| 항목 | 결정 |
| --- | --- |
| 복습 간격 끝 | 5세트 뒤에도 틀리면 큐에서 빼고 더 내지 않는다 |
| 노트 품질 피드백 | MVP에 넣지 않는다 |
| 문제 유형 | 입력 문서의 4개 유형을 MVP에 그대로 쓴다 |
| 형식·유형 확장 | 이후 서술형 등으로 늘어날 수 있다. 고정 목록으로 박지 않는다 |
| 시험 날짜 | 고려하지 않는다. LangChain MVP 일정과 무관하다 |

앞 4개는 초안 작성 중 해석이 필요했던 곳이다. 시험 날짜는 계획 1장 결정 목록에 남아 있던 항목이다.

## 도구별 평가

평가 기준은 계획 5장을 따른다. 숫자는 각 기록의 평가 메모에서 가져왔다.

| 도구 | 새로 드러낸 결정 | 바꾼 기존 결정 | 다른 도구와 겹친 질문 | 걸린 시간 |
| --- | --- | --- | --- | --- |
| paperthin `aim` | 3개(단독). 후속 대화 포함 6개 | 0개(단독). 후속 대화에서 사용자가 3개 바꿈 | 0개 | 측정 안 함 |
| gstack `/office-hours` (방법 차용) | 4개 | 4개 | 1개(웹앱 형태, 3단계에서 다시 다룸) | 측정 안 함 |
| ouroboros `interview` | 11개 | 4개 | 2개(복습 간격, 웹앱 형태) | 측정 안 함 |
| paperthin `readchk` | 1개(기존 문서 반영 범위) | 0개 | 0개 | 측정 안 함 |

### `aim`

- 잘한 점: "후보 선택보다 근거 방식(A/B)이 먼저"라는 대안 해석을 냈다. 사용자가 이 순서를 택했다. Bedrock 모델 ID와 Langfuse 호스팅 같은 미확인 사항도 처음부터 드러냈다.
- 한계: 바꾼 결정 3개는 모두 사용자의 수정이다. `aim` 단독으로 바꾼 결정은 없다.
- 비용: 낮다. 한 번 읽고 한 번 제안한다.

### `/office-hours` (방법 차용)

- 원본 스킬이 아니다. 섹션 문서의 질문 방식만 따랐다(커밋 `ad6e1db`).
- 잘한 점: 전제 공격에서 후보 선택이 뒤집혔다. 차별점(영·한 구절 매핑, 독해/개념 오답 구분)이 MVP에 들어갔다.
- 한계: 추천한 C안에 "서버 없는 단일 페이지 웹"이 들어 있었다. 이 결정은 3단계에서 사용자 지적으로 뒤집혔다. 대안을 낼 때 앱 백엔드 전제를 확인하지 않았다.
- 과제(시험 날짜 예약)는 4단계에서 "고려하지 않음"으로 정리됐다. 결과적으로 쓰이지 않았다.

### `interview`

- 잘한 점: 가장 많은 결정을 닫았다(11개). 감사 기준, 채점, 마감 축소 순서처럼 완료 조건을 숫자로 정한 것이 `requirements.md` 5장의 대부분이 됐다. 종료 점검(closer, contrarian, gap_hunter)이 1차에서 high를 내 빈칸을 한 번 더 채웠다.
- 한계:
  - 비용이 크다. 질문마다 보조 분석 6개를 돌려 질문당 대략 50만~60만 토큰이 들었다. Q4 재질문 이후 lane을 서브에이전트 하나로 묶어 줄였다.
  - code_context lane이 입력 문서 경로를 두 번 잘못 보고했다.
  - 모호성 점수가 0.21에서 0.26으로 다시 올랐다. 서버 정정 때문이다. 점수는 사용자 지적 뒤에야 움직였다.
- 0단계에서 MCP 연결 실패(`uvx` 없음)를 uv 설치로 고쳤다.

### `readchk`

- 잘한 점: 실제 갈림길 하나만 질문으로 올렸다. 나머지는 질문 없이 진행했다.
- 한계: 저절로 작동하지 않았다. 메인 세션이 호출해야 했다. 초안 작성 중 드러난 해석 항목 4개는 `readchk`가 아니라 문서를 쓰면서 나왔다.
- 비용: 낮다.

## 단계 전체

- 질문 중복: 웹앱 형태가 2단계와 3단계에서 두 번 다뤄졌다. 2단계 결정이 틀려서 생긴 중복이다. 계획 4장의 대응("확정 항목 명시")으로는 막지 못한다.
- 메인 세션 오류: 2단계의 "서버 없음" 제안, 3단계 Q2 답의 서버 전제 신호를 놓침. 사용자가 3단계 Q4 도중 지적했다.
- 산출물 중복: 계획대로 설계 문서를 따로 만들지 않았다. 결정은 `requirements.md` 하나에 모았다. 앞 기록과 입력 문서에는 안내만 달았다.
- 걸린 시간: 어느 도구도 측정하지 않았다. 다음 단계부터는 도구마다 시작·종료 시각을 기록한다.
