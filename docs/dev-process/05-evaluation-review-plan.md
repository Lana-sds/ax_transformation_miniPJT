### 이 단계에서 하는 일

03에서 앱을 만들었고, 04에서 AI 지시문을 고쳐 봤다. 05는 "만든 앱이 약속한 대로 되는가"를 증거로 확인하고, 숨은 버그를 찾는 단계다. 고치는 단계가 아니라 점검하는 단계다. 크게 셋을 한다.

1. **약속 확인**: 설계 때 정한 수용 기준 9개(예: "문제 60개", "답하기 전에는 정답이 안 보인다")를 하나씩 증거와 맞춰 본다. 테스트를 돌리고, 서버에 실제로 요청해 보고, DB를 조회한다.
2. **일부러 깨 보기**: 서브에이전트 3명에게 "이 앱을 깨 봐라"라고 시킨다. 정답이 새는지, 샌드박스(AI가 만든 코드를 격리해 돌리는 곳)를 빠져나갈 수 있는지, 채점이 틀리는지 본다. 실제로 돌려서 재현한 것만 문제로 인정한다.
3. **남은 숙제 정리**: 03, 04가 "다음 단계에서 확인"으로 넘긴 항목 16개(04 8개, 03 6개, 03 회고 2개) 중 오늘 확인할 수 있는 것을 확인한다.

찾은 문제는 `F-1`, `F-2`처럼 번호를 붙여 심각도와 함께 적는다. 마지막에 이 모두를 평가 보고서 한 장(`evaluation.md`)으로 정리한다.

이 단계는 운영 DB(`data/quiz.db`, 앱이 실제로 쓰는 데이터베이스)와 고정한 문제 60개를 바꾸지 않는다.

제품이 쓰는 기술(도구 선택 대상 아님):

- Bedrock(NFR-4): 결정 2의 교차 풀이만. `us-east-1`에서만 돈다(`quiz crosscheck` 규칙).
- Langfuse(NFR-5): 이 단계에서 새 trace를 만들지 않는다. 교차 풀이는 Langfuse에 남지 않는다(미확인. 4단계에서 확인해 기록).

고르지 않은 도구:

- gstack `/review`: "이 프로젝트의 선택" 절이 gstack을 제외했다(Windows 마찰, 배포 중심).
- paperthin `factchk`: 이 단계의 주장은 실행 증거(테스트, 재현 명령, DB 조회)로 확인한다. 외부 사실 주장이 적다. 문서 숫자 대조는 `doc` 모드 점검이 한다.
- paperthin `sip`: `shower`와 역할이 겹친다(작성 직후 자가 점검). 보조 스킬을 늘리면 호출 기록과 평가 부담만 는다(lifecycle "보조 스킬을 계획에 넣으면 호출 줄을 남긴다").
- ouroboros `evolve`, `ralph`: 결정 4. 자동 수정은 이 단계 목적과 맞지 않는다.

도구 설명 요약:

- ouroboros `evaluate`(설치본 SKILL.md, evaluation-pipeline.md, 2026-11-06):
  - 1단계 기계 검사만 승인을 줄 수 있다. 2단계 의미 검토와 3단계 합의는 승인을 막을 수만 있다. 1단계 검사가 하나도 돌지 않으면 결과는 `unverified`다.
  - 1단계 명령은 저장소 루트의 `.ouroboros/mechanical.toml`에서만 읽는다. 없으면 AI 호출 1회로 파일을 만든다. 실행 파일 허용 목록이 있다. `uv`, `npm`은 목록에 있다(`languages.py`). 셸 연산자는 막힌다.
  - 기본값 `execution.auto_evolve`가 켜져 있으면 기각 뒤 Ralph 수정 루프로 이어진다. `auto_evolve: false`로 끈다.
  - `acceptance_criteria`에 둘 이상을 주면 기준마다 따로 판정해 체크리스트로 모은다.
  - 행동 검증: 결과를 실제로 돌려 본 증거(명령 출력, 엔드포인트 응답)를 `artifact`에 넣는다.
- pstack `/interrogate`(SKILL.md, 2026-11-06):
  - 공격자마다 같은 범위, 의도, 지시문("이 변경을 깨라. 실제 코드에 실행한 결과로 증명하라")을 준다. 공격자는 자기 worktree에서 재현한다.
  - 검증: 코디네이터가 발견마다 명령을 다시 돌린다. 실패가 보이고 의도를 깨면 남긴다. 원인이 같으면 합친다.
  - 출력: 의도 재진술, 검증된 발견(명령, 출력, 의도를 깨는 방식, 찾은 공격자), 공격자별 버린 수와 이유. 고치지 않는다.
  - 원래는 공격자마다 다른 모델을 쓴다(arena 설정). 이 환경의 서브에이전트는 Claude 계열뿐이다.
- `mandela`(SKILL.md, 2026-11-06): 외부 정답이 독립적으로 들어오는지 본다. 누수 유형 8개 중 해당하는 것만 내고 보완안을 준다. 읽기 전용이다.
- `shower`(SKILL.md, 2026-11-06): 맥락 없는 서브 세션이 산출물만 읽고 막히는 곳을 진단한다. 고치지 않는다.

## 3. 진행 순서

단계 사이의 선후 관계:

```
0 → 1(mandela) → 2(evaluate) ──┐
               → 3(공격자 3명) ─┼→ 5(발견 정리, [수정 확인]) → doc(shower 포함) → retro → [06 여부]
               → 4(이월 항목) ──┘
```

- 2, 3, 4는 1 뒤에 동시에 시작한다. 2는 백그라운드 작업이고, 3은 격리 worktree 서브에이전트다. 코디네이터는 기다리는 동안 4를 한다.
- 1의 점검 결과로 2, 3의 방법이 바뀌면 바꾼 뒤 시작한다.

### 0단계: 사전 준비

1. 결정 1~3을 닫는다.
2. 04 worktree에서 `.env`, `data/quiz.db`, `data/experiments/EXP-2/arena.db`, `control.db`를 이 worktree로 복사한다(CLAUDE.md "세션과 병렬 작업").
3. `app/`에서 `uv sync`, `sandbox/`에서 `uv sync`, `web/`에서 `npm ci`를 돌린다. 04에서 `sandbox/.venv`가 없어 테스트 6개가 실패했다.
4. `cd app && uv run pytest`, `cd web && npm run build`, `npm run lint`를 돌려 결과를 기록한다.
5. `data/quiz.db`의 테이블별 행 수를 기록한다. 5단계 끝에 다시 세어 같은지 본다.
6. 이 계획과 입력 README를 커밋한다. 이 커밋이 평가 대상 커밋이고, 공격자 worktree의 기준이다.
7. 기록 파일마다 시작·완료 시각과 세션 모델을 남긴다. 추론 강도는 세션 안에서 읽지 못하면 "미확인"으로 쓴다(04 회고).

### 1단계: mandela로 평가 설계 점검

- 입력: 이 계획 1장, 2단계와 3단계 방법
- 하는 일:
  1. 맥락 없는 서브에이전트에게 `mandela`로 이 계획의 평가 방법을 점검하게 한다. 설계자(코디네이터)가 직접 점검하지 않는다(lifecycle "이 프로젝트의 선택").
  2. 미리 아는 위협을 적어 두고, 점검 결과와 대조한다.
     - 앱 코드, 테스트, 수용 기준 판정을 모두 같은 계열 모델(Claude)이 만들었다. ouroboros 2단계 검토도 Claude다.
     - 수용 기준 1~3의 증거는 03의 DB 조회 결과다. 감사는 본인 한 명이 했다.
     - 공격자 3명이 같은 계열이라 같은 곳만 볼 수 있다. 04 `/arena` 후보 2개가 같은 모양으로 모였다.
  3. 결론이 바뀌는 누수가 나오면 사용자에게 보이고, 2·3단계 방법을 고친 뒤 시작한다.
- 끝나는 조건: 점검 결과와 반영 여부가 기록됐다.
- 기록 파일: `01-mandela.md`(0단계 기록도 여기에 둔다)

### 2단계: ouroboros evaluate로 수용 기준 검증

- 입력: Seed 1.1.0, 증거 묶음
- 하는 일:
  1. `.ouroboros/mechanical.toml`을 손으로 쓴다. 자동 생성(AI 호출)에 맡기지 않는다. 명령: `uv run --directory app pytest -q`(test), `npm --prefix web run lint`(lint), `npm --prefix web run build`(build). 셸 연산자는 쓰지 않는다.
  2. 행동 검증 증거를 모은다. 모두 이 worktree에서 실제로 돌린다.
     - `mvp-checklist.md`의 측정 쿼리를 `data/quiz.db`에 읽기 전용으로 다시 돌린다(수용 기준 1~3, 8).
     - 서버를 띄우고 `POST /api/sets` 응답에 정답 키, 해설, 매핑, 근거가 없는지 본다(기준 5). 서버 환경에 `AWS_*`, `LANGFUSE_*`가 없는지 본다.
     - 기준 4, 6, 7은 해당 테스트 파일 결과를 붙인다. 기준 9는 Langfuse 환경 변수를 뺀 테스트 결과를 붙인다.
  3. `ouroboros_start_evaluate`를 부른다. `seed_content`는 seed.yaml 원문, `acceptance_criteria`는 9개 원문, `artifact`는 2번 증거, `working_dir`는 이 worktree 루트, `auto_evolve: false`(결정 4), `trigger_consensus: false`(결정 5)다.
  4. 작업이 끝나면 기준별 판정과 1단계 명령 결과를 `acceptance.md`에 옮긴다. 03 판정(implementation.md 7.2)과 다른 기준은 이유를 적는다.
- 끝나는 조건: 9개 기준과 MVP 완료 조건 4개가 `acceptance.md`에 `통과`, `실패`, `미확인` 중 하나로 있다. 1단계 기계 검사가 하나 이상 돌았다.
- 기록 파일: `02-evaluate.md`

### 3단계: interrogate 절차로 적대적 리뷰

- 입력: 범위(아래 표), 의도(Seed `goal`과 수용 기준, CLAUDE.md 고정 결정)
- 하는 일:
  1. 의도를 재진술한다. 범위는 변경분이 아니라 제품 전체다.
  2. 공격자 3명을 격리 worktree 서브에이전트로 한 메시지에서 띄운다. 지시 첫 줄은 `git reset --hard <0단계 커밋>`이고, `git log -1 --format=%H`가 같은지 확인하게 한다(stage 스킬 run 3번).
  3. SKILL.md는 모든 공격자에게 같은 범위를 준다. 이 환경은 모델이 한 계열이라 같은 곳에 모일 수 있다(04 회고). 그래서 공격자마다 중심 영역을 다르게 준다. 범위 밖 발견도 보고할 수 있다. 이 차이는 기록 파일 "계획과 다른 점"에 적는다.

     | 공격자 | 중심 영역 | 예 |
     | --- | --- | --- |
     | A | 격리와 비밀 | 샌드박스 네트워크 차단 우회(`_socket` 직접 import), 시간 제한, 서버·샌드박스에 `AWS_*`·`LANGFUSE_*` 전달, `.env` 읽는 곳 |
     | B | API와 채점 | 풀이 전 정답 노출(세트 응답, 다른 엔드포인트), 단답 정규화, 복수 선택 부분 점수, 태그 없는 오답 409, 복습 큐 전이 |
     | C | 생성 게이트와 데이터 | 인용 정규화 우회, 허용 목록 밖 페이지, 유사 중복 경계, `--resume` 멱등, 실험 명령이 `data/quiz.db`를 쓰는지 |

  4. 공격자 지시: SKILL.md의 지시문을 그대로 주고 다음을 더한다. Bedrock을 부르지 않는다. `.env`가 없다. 재현은 자기 worktree에서 가짜 모델과 임시 DB(`QUIZ_DB`)로 한다. 코드를 고치거나 커밋하지 않는다. 발견마다 제목, 정확한 명령, 출력, 의도가 요구하는 출력을 보고한다. 돌리지 않은 것은 빼고, 발견이 없어도 된다.
  5. 검증: 코디네이터가 발견마다 명령을 이 worktree에서 다시 돌린다. 실패가 보이고 의도를 깨면 남긴다. 원인이 같으면 합친다. 공격자별 버린 수와 이유를 적는다.
- 끝나는 조건: 검증된 발견 목록과 공격자별 버린 수가 기록됐다. 발견이 0이어도 끝난다.
- 기록 파일: `03-interrogate.md`

### 4단계: 이월 항목 확인

- 입력: 1.2 표의 "오늘"이 "예", "결정 2", "시간이 남으면"인 항목
- 하는 일: 위에서부터 차례로 한다. 12:00이 지나면 남은 항목은 "미확인"과 이유를 적고 멈춘다.
  1. 03 운영 Judge 입력과 실험 Judge 입력을 코드에서 대조한다.
  2. (결정 2) EXP-2 `arena` 배치 교차 풀이. 배치 ID `b20261105-01`이 운영 파일럿 배치 ID와 같아 `data/crosscheck/b20261105-01.json`을 덮어쓴다. 기존 두 파일을 먼저 복사해 두고, `QUIZ_DB=data/experiments/EXP-2/arena.db`로 돌린 뒤 결과를 `data/experiments/EXP-2/crosscheck-arena.json`, `.md`로 옮기고 원래 파일을 되돌린다. `git diff data/crosscheck/`가 비어 있는지 본다. 첫 문항 뒤 비용이 상한 2 USD를 넘을 것 같으면 멈추고 묻는다.
  3. `version_conflict` 4문항을 샌드박스로 다시 돌리고 문서 원문과 대조한다.
  4. 동시 2슬롯 유사 중복 쌍을 조회한다.
  5. 커버리지를 잰다.
  6. (시간이 남으면) `b20261105-07` 출처, Service Quotas 조회.
- 끝나는 조건: 1.2 표의 모든 항목이 `carryover.md`에 결과 또는 "미확인"과 이유로 있다.
- 기록 파일: `04-carryover.md`

### 5단계: 발견 사항 정리와 수정

- 입력: 2, 3, 4단계 결과
- 하는 일:
  1. 발견을 모아 `F-n`, 심각도(1.3), 위치, 내용, 재현 명령을 `findings.md`에 쓴다. 수용 기준 `실패`와 이월 항목에서 나온 문제도 넣는다.
  2. 결정 3에 따라 심각도별 목록을 **사용자에게 보이고, 무엇을 고칠지 묻는다**. 고르지 않은 것은 `기록만`이다.
  3. 사용자가 고른 것마다 실패하는 테스트를 먼저 쓰고 고친다. 파일이 겹치지 않는 수정이 둘 이상이면 워커로 나눈다("병렬 실행" 표).
  4. 고친 뒤 `uv run pytest`, `npm run build`, `npm run lint`와 해당 재현 명령을 다시 돌린다. `findings.md`의 상태를 `수정`(커밋 해시), `기록만`, `해당 없음` 중 하나로 바꾼다.
  5. design.md와 다른 값이 생기면 차이를 보이고 승인받은 뒤 고친다(CLAUDE.md 작업 규칙).
  6. `data/quiz.db` 행 수를 다시 세어 0단계와 같은지 본다.
- 끝나는 조건: 모든 `F-n`에 상태가 있다. 전체 테스트가 통과한다. `data/quiz.db` 행 수가 0단계와 같다.
- 기록 파일: `05-findings.md`

### 5단계 뒤

1. `doc` 모드: `acceptance.md`, `findings.md`, `carryover.md`로 `evaluation.md`를 쓴다. 장 구성을 먼저 확인받는다. 사용자에게 보이기 전에 맥락 없는 서브에이전트로 `shower`를 한 번 돌려 막히는 곳을 고친다. 기록 파일 `06-output.md`
2. `retro` 모드: 도구별 평가를 쓴다. 기록 파일 `07-retro.md`
3. 남은 시간을 보이고 06 QA를 할지 사용자에게 묻는다(lifecycle "이 프로젝트의 선택" 범위).

| 수정이 설계를 바꿈 | 보안 수정(예: 샌드박스 격리 방식)은 design.md 값을 바꿀 수 있다 | 5단계 5번. 승인 전에는 design.md를 고치지 않는다 |
| 순서에 따라 흔들리는 테스트 | 04에서 첫 전체 테스트가 17 failed였다가 다시 돌리면 통과했다. 원인 미확인 | 0단계와 5단계에 실패가 나면 한 번 더 돌리고 두 결과를 모두 기록한다. 공격자 B 또는 C가 재현하면 `F-n`으로 올린다 |
