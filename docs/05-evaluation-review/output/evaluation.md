# 평가·리뷰 보고서: LangChain 예상 문제 풀이 웹앱 (MVP)

| 항목 | 내용 |
| --- | --- |
| 문서 상태 | 확정 |
| 버전 | 1.0 (부록 B) |
| 작성일 | 2026-11-06 |

| 관련 산출물 | [acceptance.md](acceptance.md), [findings.md](findings.md), [carryover.md](carryover.md) |

이 문서는 MVP가 요구사항과 수용 기준을 지키는지 평가한 결과다. 판정 기준은 요구사항 정의서와 Seed다. 둘이 다르면 요구사항 정의서를 따른다.

## 쉬운 설명

03에서 앱을 만들었고, 04에서 AI 지시문을 고쳐 봤다. 이 단계는 "만든 앱이 약속대로 되는가"를 증거로 확인하고, 숨은 버그를 찾았다.

- **약속 확인**: 수용 기준 9개와 MVP 완료 조건 4개가 지금 데이터에서 모두 통과다. 테스트만 보지 않았다. 앱 코드를 쓰지 않는 별도 스크립트로 DB를 다시 계산했고, 코드를 보지 않은 검토자가 요구사항만 보고 만든 사례 40개를 실제 API에 돌렸다.
- **일부러 깨 보기**: 세 갈래로 공격해 버그 19개를 찾았다. 06 테스트를 준비하며 다른 작업 공간에서 화면을 미리 눌러 본 결과에서 1개(F-20)를 더했다. 모두 20개다(높음 5, 중간 10, 낮음 5). 가장 큰 것은 샌드박스(AI가 쓴 코드를 격리해 돌리는 곳)다. 그 코드가 자격 증명 파일을 읽고 밖으로 보낼 수 있었다. 고정한 문제 풀이 나중에 바뀌거나 중복 문제가 들어가는 경로도 있었다. 높음 5개는 고쳤다(4.2).
- **남은 숙제**: 03, 04가 넘긴 14개 중 8개를 확인했다(일부만 확인 2개 포함). 6개는 비용이나 사람이 필요해 미확인으로 남겼다. 고정 풀 안에 같은 인용을 쓰는 문제 쌍 3개가 실제로 있다. 데이터는 바꾸지 않고 기록만 했다.

판정: 06 테스트 단계로 진행한다. 조건은 6.2에 있다.

이 문서를 읽는 데 필요한 말:

| 말 | 뜻 |
| --- | --- |
| 수용 기준 | 설계 때 "이렇게 되면 완성"이라고 정한 약속 9개. Seed라는 파일에 있다 |
| 고정 풀 | 출제에 쓰려고 확정해 둔 문제 60개 목록 |
| 버킷 | 문제 주제 묶음 6개(RAG, LangGraph 기초 등) |
| Judge | 생성된 문제를 검사하는 AI. 정답이 맞는지, 근거가 정답을 뒷받침하는지 본다 |
| 결정적 게이트 | AI 없이 코드로 하는 검사. 인용이 문서에 그대로 있는지, 번역 대응표가 있는지, 코드 문제의 실행 결과가 맞는지 |
| 감사 | 본인이 문제 20개를 직접 읽고 오류를 표시한 점검 |
| 샌드박스 | 코드 문제의 보기 코드를 격리해서 실행하는 곳 |
| arm | 실험에서 비교한 조건 하나(예: 원래 지시문, 고친 지시문) |

## 1. 개요

### 1.1 목적

이 문서는 MVP 구현의 수용 기준 충족 여부, 리뷰 발견 사항, 품질 지표, 잔여 위험을 정의한다. 06 테스트 단계는 이 문서를 기준으로 한다.

### 1.2 단계 목표

| 목표 | 관련 요구사항 |
| --- | --- |
| Seed 수용 기준 9개와 MVP 완료 조건 4개를 실행 증거로 판정한다 | 요구사항 7.1, Seed |
| 정답 노출, 비밀 유출, 격리 탈출, 데이터 손상 경로를 찾는다 | FR-2.1, GR-7, NFR-3.2 |
| 03, 04가 넘긴 확인 항목을 닫거나 이유와 함께 남긴다 | 요구사항 7.3, NFR-4, NFR-5 |
| 운영 DB와 고정 풀을 바꾸지 않는다 | C-1 |

### 1.3 범위

- 평가 대상은 제품 전체다. 변경분만 보지 않았다.
- 수정은 심각도 "높음"만 했다. 나머지는 기록만 했다.
- 운영 DB `data/quiz.db`와 고정 풀 `ps_326384fb5422`는 바꾸지 않았다.
- 범위 밖 항목은 부록 A에 있다.

### 1.4 용어 정의

요구사항 정의서 1.4, 실험 결과서 1.5의 용어를 그대로 쓴다. 자주 나오는 말은 "쉬운 설명" 끝 표에 있다. 이 문서에서 더하는 용어는 다음과 같다.

| 용어 | 뜻 |
| --- | --- |
| 보장 | 지금 데이터가 아니라 앞으로의 데이터에 대해 기준이 지켜지는지. 깨뜨리는 재현 경로가 있으면 "약함"이다 |
| 독립 재계산 | 앱 패키지를 import하지 않는 스크립트로 DB 값을 다시 계산하는 것 |
| 사례 표 | 코드를 보지 않은 검토자가 Seed와 요구사항만 읽고 만든 입력·기대 결과 목록(K-1~K-40) |
| 적대적 리뷰 | 제품을 깨뜨리는 시도를 실행으로 증명하는 리뷰. 공격 영역을 격리·비밀, API·채점, 생성 게이트·데이터 셋으로 나눴다 |

### 1.5 표기

- ID 체계: `F-n`은 리뷰 발견 사항이다. `E0`~`E4`는 이 문서의 증거 묶음이다(2.3).
- 판정 값: `통과`, `실패`, `미확인`.
- 심각도: 높음(요구사항이나 고정 결정 위반. 정답 노출, 비밀 유출, 격리 탈출, 데이터 손상), 중간(기능이 틀리지만 우회할 수 있거나 드문 입력에서만), 낮음(문서, 가독성, 유지보수).
- 조치 값: `수정`(커밋), `기록만`.
